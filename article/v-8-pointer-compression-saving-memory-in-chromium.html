V8 Pointer Compression: Saving Memory in Chromium

Pointer compression in the V8 JavaScript engine is an optimization technique that drastically reduces memory consumption in the Chromium web browser by shrinking the size of memory pointers from 64 bits to 32 bits. By storing pointers as smaller offsets relative to a base address rather than full memory addresses, Chromium significantly lowers its RAM usage without sacrificing the performance and security benefits of 64-bit architectures. This article explores why 64-bit pointers became a problem, the exact mechanics of pointer compression, and how this technique saves memory in your browser.

The Problem with 64-Bit Pointers

When operating systems and web browsers transitioned from 32-bit to 64-bit architectures, applications gained access to a vastly larger address space, improved performance, and better security features. However, this transition came with a major downside: it doubled the size of every memory pointer from 4 bytes (32 bits) to 8 bytes (64 bits).

Because JavaScript is a dynamically typed language, the V8 engine represents almost all data as objects allocated on a memory space called the heap. V8 relies heavily on pointers to reference and connect these objects. Consequently, doubling the size of every pointer caused a massive surge in Chromium's memory consumption, as the vast majority of the V8 heap consists of these pointers.

How Pointer Compression Works

In reality, a single web page rarely needs the massive 16 exabytes of memory that a 64-bit pointer can theoretically address. Recognizing this, the V8 team introduced pointer compression to get the memory savings of 32-bit pointers while running on 64-bit hardware.

Pointer compression works through a "base plus offset" model:

  1. The 4GB Sandbox: V8 allocates all of its heap objects within a single, contiguous 4-gigabyte (GB) region of virtual memory.
  2. The Base Address: The starting point of this 4GB memory region is called the base address. This full 64-bit address is stored in a dedicated CPU register so it can be accessed instantly.
  3. The 32-Bit Offset: Because all objects live within that 4GB boundary, V8 does not need to store the full 64-bit address for every object. Instead, it only stores a 32-bit offset—the distance of the object from the base address.

When V8 needs to access an object in memory, it takes the 32-bit compressed pointer from the heap and adds it to the 64-bit base address stored in the CPU register. This "decompression" reconstructs the full 64-bit address on the fly. When V8 writes a pointer back to memory, it simply drops the upper 32 bits, compressing it again.

How It Saves Memory in Chromium

By cutting the size of heap pointers in half, pointer compression directly shrinks the memory footprint of every open tab and extension in the Chromium browser.

In real-world browsing scenarios, pointer compression reduces the size of the V8 heap by up to 40%. Because the V8 heap is one of the largest consumers of memory in modern web applications, this translates to an overall memory reduction of roughly 20% across the entire Chromium browser renderer process.

Beyond saving gigabytes of RAM, pointer compression also improves CPU performance. Because the compressed pointers are twice as small, the CPU can pack twice as many of them into its ultra-fast L1, L2, and L3 caches. While decompressing a pointer requires an extra math instruction (adding the base and the offset), the time saved by fetching smaller chunks of data from the CPU cache completely offsets the cost of that calculation, making Chromium both lighter and faster.
