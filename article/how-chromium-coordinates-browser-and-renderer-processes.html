How Chromium Coordinates Browser and Renderer Processes

This article explores the multi-process architecture of the Chromium web browser, specifically focusing on how the central browser process manages and communicates with multiple isolated renderer processes. By utilizing asynchronous Inter-Process Communication (IPC) via the Mojo framework, shared memory, and strict sandboxing, the main browser process orchestrates the creation, resource allocation, and lifecycle of numerous renderer processes. This coordination ensures that complex web pages load efficiently, securely, and independently without compromising the stability of the entire browser.

Defining the Roles

To understand how coordination works, it is necessary to distinguish between the two process types:

  • The Browser Process: There is only one main browser process. It acts as the control center, managing the user interface (tabs, toolbars), handling disk and network access, and orchestrating all other processes. It has full access to the operating system.
  • Renderer Processes: There are multiple renderer processes running simultaneously. Each renderer contains the Blink rendering engine and the V8 JavaScript engine, which work together to turn HTML, CSS, and JavaScript into an interactive web page. For security, renderers run in a restricted "sandbox" with no direct access to the operating system, file system, or network.

Process Creation and Site Isolation

The browser process decides when to create or destroy a renderer process based on navigation events and a security feature called Site Isolation.

When a user types a URL into the address bar, the browser process initiates the navigation. Instead of simply using one renderer per tab, Chromium uses a "process-per-site-instance" model. The browser process checks the domain of the requested URL. If the user is navigating to a new domain, the browser process spawns a brand-new renderer process dedicated to that specific site.

Even if a single web page contains multiple <iframe> elements from different domains, the browser process will spin up separate renderer processes for each iframe and stitch them together visually. The browser process maintains an internal map—using classes like RenderFrameHost—to keep track of which renderer process belongs to which tab or frame.

Communication via the Mojo IPC Framework

Because renderer processes are sandboxed, they cannot fetch data, save files, or access hardware on their own. They must ask the browser process to do it for them. Chromium handles this through Inter-Process Communication (IPC), specifically using a system called Mojo.

Mojo establishes bidirectional "message pipes" between the browser process and each renderer process. Coordination through Mojo works as follows:

  1. Asynchronous Messaging: Communication is strictly asynchronous. When a renderer needs information (like system clipboard data) or wants to notify the browser of an event (like a page title changing), it sends a Mojo message and continues working. This prevents the browser UI from freezing if a renderer is slow or unresponsive.
  2. Strongly Typed Interfaces: Developers define Mojo interfaces (using .mojom files) that act as strict contracts. The browser process exposes specific interfaces to the renderer. When the renderer calls a method on an interface, Mojo serializes the data, sends it across the pipe, and triggers the corresponding implementation in the browser process.
  3. Security Validation: Because a renderer process can be compromised by malicious JavaScript, the browser process treats all incoming IPC messages as untrusted. The browser process validates every request to ensure the specific renderer actually has the permission to access the requested data.

Sharing Data and System Resources

Passing large amounts of data—such as images, video streams, or large HTML files—over Mojo message pipes would be too slow. To coordinate heavy data transfers efficiently, the browser process uses Shared Memory.

When a renderer needs a web resource (like an image), the coordination happens in steps:

  1. The renderer requests the URL via Mojo.
  2. The browser process coordinates with the Network Service to download the data from the internet.
  3. The browser process allocates a block of shared memory (RAM that both processes are allowed to read) and writes the downloaded data into it.
  4. The browser sends a lightweight Mojo message to the renderer containing a "handle" (a pointer) to that shared memory block.
  5. The renderer reads the data directly from the memory block without the operating system needing to copy the data from one process to another.

Managing Lifecycles, Priority, and Crashes

The browser process acts as a task manager for all active renderer processes, constantly monitoring their health and resource usage.

  • Prioritization: The browser process knows which tabs are visible to the user and which are hidden in the background. It communicates with the operating system to lower the CPU priority of background renderer processes, ensuring that the active tab gets the most system resources.
  • Memory Management: If the system runs low on RAM, the browser process can instruct background renderers to purge their caches, or it can completely terminate a background renderer, saving its state so it can be reloaded if the user clicks the tab again.
  • Crash Handling: The browser process monitors the IPC pipes connected to each renderer. If a renderer hits a fatal error (such as an out-of-memory crash or an infinite loop), the IPC pipe breaks. The browser process immediately detects this disconnection, cleans up the dead process's resources, and replaces the web page viewport with the "Aw, Snap!" error screen. Because the browser process remains unaffected, all other tabs and renderer processes continue functioning normally.
