Inside Chromium: GPU Hangs and Context Lost Recovery

This article provides a quick overview of the internal mechanisms triggered inside the Chromium web browser when its Graphics Processing Unit (GPU) process becomes unresponsive. It covers how a dedicated watchdog thread detects the freeze, deliberately terminates the hung process, and initiates a "context lost" recovery sequence to seamlessly restore visual rendering for both the browser interface and web content without crashing the entire browser.

The GPU Process and the Watchdog Thread

Chromium isolates hardware-accelerated graphics operations into a dedicated GPU process. Because third-party graphics drivers can be unstable and complex shaders can trigger infinite loops, the GPU process is constantly at risk of freezing.

To handle this, the GPU process spawns a secondary monitoring thread called the GpuWatchdogThread alongside its main thread. As the main GPU thread processes rendering commands, it periodically updates a shared progress counter. The watchdog thread wakes up at regular intervals to check this counter, verifying that the main thread is still actively processing tasks.

Detecting the Hang and Forcing Termination

A GPU hang occurs when the main thread gets stuck—typically while waiting on a blocked system call inside a graphics driver or executing an excessively heavy WebGL operation. When this happens, the main thread fails to update the progress counter.

If the GpuWatchdogThread wakes up and sees that the main thread has not made progress within a specific timeout period (usually between 15 to 25 seconds, depending on the operating system), it declares the GPU process hung. Because a thread blocked inside a kernel-level graphics driver cannot be safely interrupted, the watchdog thread takes drastic action: it deliberately crashes the entire GPU process. This forced termination frees the locked hardware resources and generates a crash report for browser engineers.

Severed IPC Channels and "Context Lost"

The GPU process communicates with the main Browser process and various Renderer processes using Chromium's Inter-Process Communication (IPC) system, known as Mojo.

When the watchdog terminates the GPU process, the operating system immediately closes the GPU end of these Mojo pipes. The Browser and Renderer processes detect this abrupt disconnection as a channel error. Internally, Chromium translates this broken connection into a "Context Lost" state. This means all state held in the GPU's memory—including textures, vertex buffers, compiled shaders, and command buffers—has been wiped out and is no longer accessible.

Rebuilding the Process and Display Compositor

The Browser process orchestrates the recovery immediately after detecting the lost context:

  1. Spawning a New Process: The Browser process launches a brand-new, clean GPU process.
  2. Restoring Viz: It re-initializes the display compositor (known as Viz) inside the new GPU process.
  3. Redrawing the UI: The Browser process creates a new rendering context for itself, re-uploads the textures required for the browser's user interface (such as the tab strip and address bar), and resumes drawing the browser window.
  4. Reconnecting Renderers: The Browser process establishes new IPC channels between the surviving Renderer processes and the new GPU process.

Restoring Web Content and WebGL

How web content recovers from a context loss depends on how the webpage is being rendered.

For standard HTML, CSS, and 2D DOM elements, the recovery is handled automatically by the Renderer's compositor. Once connected to the new GPU process, the Renderer allocates new GPU memory, re-rasterizes the webpage's visual tiles, and submits a new frame to the display compositor. To the user, this is completely seamless, resulting in nothing more than a brief visual flicker or a momentary pause in scrolling.

For web applications that directly control the GPU via WebGL or WebGPU, Chromium cannot automatically rebuild the lost state because it does not retain copies of the raw data sent by the application's JavaScript. Instead, Chromium relies on web standard events:

  • When the GPU process dies, the Renderer fires a webglcontextlost event at the HTML5 Canvas element.
  • Once the new GPU process is running and ready to accept commands, Chromium fires a webglcontextrestored event.
  • A well-written web application listens for this restoration event and manually re-uploads its textures, geometry, and shaders to resume rendering.

Fallback to Software Rendering

Sometimes a specific graphics driver bug or a malicious webpage will cause the GPU process to hang again immediately after it recovers. To prevent an infinite loop of crashes and recoveries, the Browser process tracks how many times the GPU process dies within a short window.

If the crash count exceeds a strict threshold, Chromium abandons hardware acceleration entirely. It disables the physical GPU and restarts the rendering pipeline in software mode, utilizing a CPU-based rasterizer (such as SwiftShader) to ensure the browser remains stable and functional for the user.
